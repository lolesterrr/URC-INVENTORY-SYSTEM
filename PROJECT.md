# PROJECT.md — Persistent Plan & Memory

> This file is our external memory. Update it **before** writing code. Keep entries short.

## 1. Objective
Turn the internship prototype into a production-grade, **self-hosted** IT inventory system for Uganda Railways Corporation:
- Hosted on a URC **Windows Server** and reached by computers on the internal network.
- **Internal database** with no cloud dependency, plus **scheduled automatic backups** and a tested restore.
- Harden security, fix pitfalls, and add the features that established asset-management products provide.

## 4. Architecture decisions
| ID | Decision | Status |
|---|---|---|
| D1 | Keep React + Express/TypeScript and reuse the UI. | ✅ Agreed |
| D2 | **SQLite** via `better-sqlite3` (WAL mode) with **Drizzle ORM** and migrations. DB file lives outside the repo (e.g. `C:\URC-Inventory\data\inventory.db`, path from `.env`). 300 assets growing to tens of thousands is far below SQLite's limits. | ✅ Agreed |
| D3 | **Local accounts only**: about 4–5 users, so no Active Directory. The Admin creates accounts and there is **no self-registration**. Passwords are hashed with argon2id. Server-side sessions use an httpOnly cookie, with a 30-minute idle timeout. The account locks after 5 failed logins. Users must change the initial password on first login. | ✅ Agreed |
| D4 | Roles and permissions are enforced by server middleware. See §4a. | ✅ Agreed |
| D5 | Hosting: Node runs as a **Windows Service** via NSSM, self-contained, with no IIS dependency. HTTPS certificate files are configured through `.env`; the certificate itself comes from URC IT at deployment. The step-by-step runbook will be written for someone new to Windows Server. | ✅ Agreed |
| D6 | Backups: in-app scheduler (nightly, 02:00) using the SQLite online backup API. Files are timestamped and checked with `PRAGMA integrity_check`. Retention is 7 daily, 4 weekly and 12 monthly. There is an optional second copy path (network share or other disk), plus a "Backup now" button, a restore script and a restore drill. | ✅ Agreed |
| D7 | **Remove Firebase and the Gemini AI assistant.** The Gemini free tier has usage limits, needs the server to reach the internet, and Google's free-tier terms allow it to use submitted data to improve its products, so URC asset data would leave the organisation. Can be revisited later as an opt-in feature. | ✅ Agreed |

### 4a. Roles
| Role | Who | Permissions |
|---|---|---|
| **Admin** | The developer during build and handover, **plus one permanent URC IT staff member** (at least 2 admins so nobody gets locked out) | Everything, plus managing users, backups and restore, and settings. Use this account only for admin tasks. |
| **IT Officer** | The 2 IT technicians | Create and edit assets, check out and check in, manage departments, locations and staff (`directory:manage`, shared with Admin), run physical audits, import and export CSV, print labels. Cannot manage users or delete the audit log. Delete is a soft delete. |
| **Manager** | The system analyst (liaison to the board) | View everything, reports and dashboards, export, **approve disposals and write-offs**. No hands-on editing. Named "Manager" rather than "Department Head", which could be confused with other URC department heads. |
| **Auditor** | Internal audit | Read-only view of everything, including the full change history, plus export. |

- [x] T9e CSV import for the hardware register (2026-10-16). `docs/FEATURE_COMPARISON.md` §F marks "CSV / Excel import with column mapping and validation" **Must (v1)**. The export was already column-driven; the gap was getting a spreadsheet *into* the register — above all the purchase and warranty details T9d added, which no legacy data holds.
  - **Decisions taken with the user (2026-10-16):**
    - **Rows are matched on `Asset ID`, and the import both updates and adds.** An ID already in the register is updated, a valid ID that is not is added, and a blank one is a rejected row. Asset ID is the primary key and the first column of every export, so export → edit in Excel → import round-trips. **Serial number is deliberately not a match key:** `serial_number` has no unique index, many are blank, and two assets sharing one would be ambiguous.
    - **Unknown departments and locations are named in the preview and created only when asked** (`createMissingDirectory`, a checkbox in the dialog). Silent `findOrCreate*`, which `npm run import-json` uses, is how the legacy duplicates arrived and why T9c had to build merge; requiring an exact match instead would mean a long fix-the-sheet-and-retry loop.
    - **One audit entry per changed asset, plus one batch summary.** Each asset's own History shows `Import Hardware` with before/after values; the `CSV Import` entry records rows read, added, updated, unchanged and rejected, and the directory records created. A batch-only entry would have repeated the known T9c merge gap, where an asset's History does not show what a merge changed.
  - **API:** `POST /api/hardware/import {csv, dryRun, createMissingDirectory}` (`assets:write`). The file arrives as text and is parsed on the server, so the server decides what may be written. `createMissingDirectory` additionally needs `directory:manage`. The route takes a 6 MB JSON body (the rest of the API keeps 1 MB) and at most 5,000 rows.
  - **The dry run is the same code path.** The whole import runs inside one transaction and is rolled back when `dryRun` is set, so the preview is exactly what a commit does — audit entries included. A commit is one transaction too: every accepted row is applied or none is.
  - **Not settable by import:** `lifecycleState` and the assignee, which have their own endpoints — the same fields `PUT` already ignores. The `State` and `User / Assignee` columns an export writes are read and left alone, and the preview says so rather than failing. An asset added by an import starts **In Stock** with no assignee. A column that merges two fields (`OS / Details`, `Firmware / OS`) is also left alone rather than guessing which field the editor meant; `Operating System` and `Firmware Version` set them unambiguously.
  - **Blank cells:** a column **absent** from the file is never touched, so a two-column sheet (`Asset ID`, `Purchase Cost (UGX)`) updates only costs. A **blank cell in a column that is present** clears that field, which is what makes the round trip lossless. An empty cost is stored as NULL, never 0. Two fields have no empty state: a blank `Asset Name` is a rejected row, and a blank `Category` leaves the category as it is (a new asset falls back to `detectCategory`).
  - **Rows are rejected one at a time, with a reason, and the rest of the file still goes in:** a blank or malformed `Asset ID`, an ID repeated in the file, a Disposed asset (read-only, as for `PUT`), an archived asset (restore it first), a value its own field schema refuses, a new asset in a file with no name column, an ambiguous bare location name, or a new reference to an archived record.
  - **Headers** are matched ignoring case and spacing, against the headers the export writes, including each register's own names (`Device Name`, `Server Name`, `Printer Name` all mean the asset name; `Rack / Room Location`, `DC Location`, `Office Location` all mean the location). Unrecognised columns are listed in the preview, never fatal. Money may be written `1,200,000` or `UGX 1,200,000`.
  - **Locations** match on the full path the export writes (`Central / Kampala / HQ`). A bare name that could be any of several is a rejected row naming the candidates. Creating is offered only for a top-level name: an unknown nested path is refused and points at the Directory screen, so an import can never invent a hierarchy.
  - **Shared code:** `shared/csv.ts` now holds the RFC 4180 reader as well as the `csvCell`/`toCsv` writer moved out of `src/components/inventory/model.ts`, so the export and the import cannot drift apart. The reader undoes the `'` formula guard the writer adds, and only in that exact case, so a condition note like `-- faulty` survives a round trip. `detectCategory` and the audit snapshot helper moved to `server/services/hardware.ts` so services never import routes.
  - **UI:** a "CSV IMPORT" button beside CSV EXPORT on the hardware register (hardware tab only, disabled without `assets:write`) opens `ImportDialog`: counts, the rows with rejected ones first and their reasons, the directory records that would be created, and the columns read but left alone. Ticking the checkbox re-runs the preview, so the screen always matches what the import will do.

- [x] T9b Check-out / check-in (2026-10-05).
  - Design decision: **Deployed is reached and left only through check-out and check-in.** `shared/lifecycle.ts` no longer lists Deployed as a destination of any other state, so `POST /api/hardware/:id/lifecycle` rejects a direct move to or from Deployed (with a hint pointing at check-out/check-in) and the "Change state" dialog never offers it. This keeps the invariant that a Deployed asset always has exactly one open assignment row.
  - Data: new `asset_assignments` table (id, hardware_id, assignee, checked_out_at, checked_out_by, due_back, checked_in_at, checked_in_by, notes). A partial unique index (`checked_in_at IS NULL`) enforces at most one open row per asset. Migration `0003_checkout_checkin.sql` (hand-written `--custom` SQL; snapshot regenerated from the schema, same process as 0002) creates the table and backfills an open assignment for every asset that is already Deployed with a real assignee, using the last lifecycle-change time (or creation time) as the check-out time and `system` as who checked it out.
  - API: `POST /api/hardware/:id/checkout {assignee, dueBack?, notes?}` moves In Stock or In Repair → Deployed, needs `assets:write`, and 409s if the asset is in another state or already has an open assignment. `POST /api/hardware/:id/checkin {notes?}` closes the open assignment; a Deployed asset returns to In Stock, one that is In Repair (sent for repair without going through check-in first) stays In Repair but its assignee is released. `GET /api/hardware/:id/assignments` (`assets:read`) lists every cycle for an asset, newest first, open one included.
  - Decided: an asset can be sent **Deployed → In Repair** directly through "Change state" without checking in — the same person is assumed to get it back, so the assignment stays open. Moving an asset **into In Stock, Retired or Disposed** through "Change state" (not just through check-in) always closes any open assignment and clears the assignee, so the invariant holds whichever path is used. A new asset can still be created already Deployed (as in T9a); doing so with an assignee now also opens an assignment.
  - UI: green "Check out" / blue "Check in" row actions (shown only for the states that allow them), each opening a small dialog (`src/components/inventory/AssignmentDialogs.tsx`); check-in shows who the open assignment is with and the due-back date first. Both actions and audit entries ("Check Out" / "Check In") show up in the existing History dialog, so no separate history UI was needed. The Barcode Scan Center gained the same two buttons; its own "Lifecycle state" quick-dropdown can no longer reach Deployed (by design), and its assignee field is now labelled "record only" since editing it there no longer deploys the asset.
